# Ember Camp 模块化重构设计

## 1. 目标和边界

本设计针对 `C:\projects\game` 当前的 Godot 4.7.2 项目。目标不是重新设计玩法，而是让后续按功能创建 worktree 时，功能分支可以跨越自己需要的多个目录，同时尽量不修改其他功能的内部实现，从而降低合并冲突和回归定位成本。

第一阶段严格限制为代码组织重构：

- 不改变单主角探索主循环、交互 ID、奖励、碰撞、输入、HUD 视觉和游戏结束规则。
- 不改变 `SAVE_VERSION` 和现有存档顶层语义。
- 不改变现有公开入口的行为。旧入口通过兼容门面转发到新模块，迁移完成并经过回归后才考虑删除。
- 音频系统保持当前 `AudioService` 架构，除非某个边界迁移确实需要适配，不在本设计中重新设计音频。
- 不引入 Web UI、第二套资源账本、第二套事件管理器或全局万能 `EventBus`。

## 2. 当前审计结论

当前 `scenes/Main.tscn` 只有一个 `Main` 节点，`scripts/main.gd` 在运行时创建并连接 `GameManager`、`ExplorationWorld` 和 `UIController`。这种运行时组装本身可以保留，但职责目前集中在少数热点文件：

- `scripts/ui_controller.gd` 约 2028 行，同时负责控件构建、窗口状态、输入回调、制作/建造/存档调用和状态刷新。
- `scripts/exploration_world.gd` 约 905 行，同时负责地图绘制、装饰、碰撞、交互点注册、室内切换、施工点恢复和音频上下文。
- `scripts/game_manager.gd` 约 775 行，同时拥有阶段切换、资源、时间、生存、任务、事件、建造、炉火、温度、存档和音频适配逻辑。
- `scripts/resource_manager.gd` 约 487 行，同时管理资源总账、背包、储物、容量、鱼、烹饪和工具。

测试已经覆盖较多行为，但测试脚本大多位于 `tests/` 根目录，并直接访问这些热点对象的内部属性。这些测试是重要的行为锁，不能在第一阶段一次性改写；新模块测试应增加在按领域划分的子目录中。

## 3. 设计决策

### 3.1 采用渐进式领域拆分

采用“新增实现 -> 兼容门面转发 -> 调用迁移 -> 删除旧实现”的顺序。`GameManager`、`ExplorationWorld` 和 `UIController` 的路径及公开入口在兼容期内保留，避免一轮大规模重命名同时改变脚本加载、场景生命周期和测试调用。

考虑过的替代方案：

1. 事件总线驱动的全面解耦。长期边界可能更纯，但当前状态时序和存档依赖复杂，调试路径会变长，回归风险高，因此只在确有跨模块通知需求时使用显式信号。
2. 完全按场景重做。会同时改动 `Main.tscn`、输入、相机、存档和大量动态节点，迁移期冲突会集中到共享文件，因此延后。

### 3.2 依赖方向

```text
Main / 组合根
  -> application / 游戏流程编排
      -> domain / 资源、生存、建造、进度、事件
      -> infrastructure / 存档、音频
  -> world / 空间、地图、交互、室内
  -> presentation / HUD、窗口、主题
```

- `Main` 负责创建对象、连接信号、转发输入和驱动一帧。
- 应用层负责流程编排，不绘制地图、不创建 HUD 控件。
- 领域层不依赖 `UIController`、`ExplorationWorld` 或场景树；不通过 `get_parent()`、`/root/Main` 查找服务。
- 世界层负责空间和交互触发，交互结果交给领域服务处理。
- 表现层只消费状态快照并发出用户意图，不直接修改资源字典、阶段字段或存档结构。
- 存档基础设施只负责 JSON 文件读写和迁移协调；每个领域模块负责自己的序列化内容。
- 音频通过现有 `AudioService` 访问。不得从新领域模块选择音频文件或创建播放器。

GDScript 新类型优先使用显式 `preload()`。只有在解析顺序稳定、确实需要全局类型名时才新增 `class_name`，避免此前出现过的类型声明顺序问题。

## 4. 目标模块和职责

目标目录是职责地图，不要求一次性创建所有目录；每个迁移阶段只建立当阶段所需的文件。

```text
scripts/
  core/                 # 稳定结果、快照和事件载荷约定
  application/          # 游戏流程编排；GameManager 是过渡门面
  domain/
    inventory/          # 资源目录、背包、储物、容量、原子奖励、工具
    survival/           # 日循环、夜间结算、温度、火源、生存策略
    construction/       # 建造、蓝图、施工技能和施工项目
    progression/        # 任务、事件、里程碑
  world/
    map/                # 地图布局、绘制、碰撞和相机边界
    interaction/        # 交互注册、范围检测和交互状态机
    interior/           # 小屋、床、炉火和进出屋
  presentation/
    hud/                # 常驻 HUD 和资源/状态信息
    overlays/            # 暂停、背包、储物、制作、建造、事件和报告
    theme/              # 现有 pixel_ui_theme 和图标适配
  infrastructure/
    persistence/        # SaveSystem 和存档协调
    audio/              # 现有 AudioService 及控制器
```

具体迁移归属：

| 当前文件 | 目标职责 | 兼容期责任 |
| --- | --- | --- |
| `scripts/game_manager.gd` | 流程门面，持有领域协作者并协调阶段变化 | 保留旧属性和入口；不再新增具体业务分支 |
| `scripts/resource_manager.gd` | 资源门面 | 转发到 `inventory` 和资源目录模块 |
| `scripts/exploration_world.gd` | 世界运行时门面 | 组合地图、碰撞、交互和室内组件 |
| `scripts/interaction_point.gd` | 交互状态机 | 通过注入的服务提交结果，不调用 UI |
| `scripts/ui_controller.gd` | UI 组合和兼容门面 | 子控制器只拥有自己的控件、状态和意图回调 |
| `scripts/main.gd` | 组合根和输入路由 | 仍是唯一每帧入口，不承载领域规则 |
| `scripts/save_system.gd` | JSON IO | `SaveCoordinator` 负责模块片段组装/恢复 |
| `scripts/audio_*.gd` | 音频基础设施 | 维持现有语义事件和快照接口 |

资源领域优先拆成资源目录、背包/储物状态和原子资源操作三个协作者；工具和烹饪只有在拥有独立状态或独立测试时才继续拆分。生存领域优先把日循环、夜间结算、温度/火源和策略状态分开，但仍由 `GameManager` 负责调用顺序。世界领域优先分离绘制、碰撞、交互注册和室内生命周期；地图常量保持一个权威来源。

## 5. 稳定接口契约

第一阶段不强行引入复杂 DTO。先以文档化的 `Dictionary` 契约配合显式 `preload()`，等调用稳定后再将高价值契约升级为小型 `RefCounted` 类型。

- 领域命令返回 `{ok, reason, changed, data}`；失败不得隐式扣资源、推进时间或改变阶段。
- 领域状态提供 `snapshot() -> Dictionary` 只读视图。UI 不直接遍历多个系统的可变字典。
- 交互、建造和日循环信号只携带稳定 ID、进度和结果数据，不携带 `Node`、控件或场景路径。
- 存档顶层继续使用现有版本和兼容字段；新增协调器按 `session`、`inventory`、`survival`、`construction`、`world`、`events`、`tasks` 等内部片段收集和恢复，再映射到现有顶层字段。片段是代码责任划分，不代表新增存档语义；结构重构不提高存档版本号。
- 兼容入口包括但不限于 `GameManager.resources`、`GameManager.finish_exploration_day()`、`UIController.toggle_backpack()`。这些入口只能转发，不能再成为新逻辑的落点。
- 新模块通过最小依赖注入取得所需服务。禁止新增跨模块的 `get_parent()`、单例路径查找和对方内部字典写入。

## 6. 面向功能的 worktree 模型

worktree 按“垂直功能切片”组织，而不是按目录硬隔离。一个功能可以同时拥有领域实现、世界适配、表现层窗口和测试，只要这些文件都服务于同一个功能。

每个功能 worktree 应登记以下内容：

- 主功能 ownership，例如鱼处理、建造预览、温度提示或储物交互。
- 可自由修改的功能文件和必须最小化修改的兼容适配文件。
- 使用的稳定接口和存档/信号契约。
- 可能与其他 worktree 冲突的共享入口。

例如“鱼处理”可以包含：

```text
scripts/domain/inventory/fish_processing.gd
scripts/world/interaction/fishing_adapter.gd
scripts/presentation/overlays/fish_processing_view.gd
tests/fishing/
```

受保护文件是 `project.godot`、`scenes/Main.tscn`、`scripts/main.gd`、兼容门面和回归 runner。它们由集成 worktree 维护。功能分支如果必须改变门面，只提交最小转发或信号适配，不把新业务逻辑塞回热点文件。

不做全目录格式化；不在同一提交中混合大规模移动和行为改变。每个切片保持独立解析和测试，合并顺序为：契约 -> 资源 -> 生存 -> 世界 -> HUD -> 存档/清理。可选的新功能自动发现机制可以在核心边界稳定后单独评估，第一阶段不依赖它。

## 7. 迁移阶段

### 阶段 0：基线和契约

记录编辑器解析、现有回归、音频回归和 960×540/1920×1080 运行截图。新增 `scripts/core/` 的最小契约、架构规则文档和静态边界检查，但不改变运行行为。该阶段先合并，作为后续 worktree 的共同基线。

### 阶段 1：资源和背包

从 `ResourceManager` 提取资源目录、背包/储物状态和原子资源操作。保留所有旧方法。新增资源领域单元测试和门面等价性测试；原有烟测先不改写。

### 阶段 2：日循环和生存

从 `GameManager` 提取日循环、夜间结算、温度/火源和策略协作者。保持唯一的 `advance(delta)` 和床边结束当天规则，保留旧的 `start_exploration`、`tick`、`finish_day` 等兼容入口。该阶段完成后再让世界和 HUD 依赖新的稳定接口。

### 阶段 3：世界和交互

将 `ExplorationWorld` 的地图绘制、碰撞构建、交互注册和室内生命周期拆成协作者。保持当前节点创建方式、地图常量、室内偏移和交互 ID。资源点只负责描述动作，奖励提交走领域服务。

### 阶段 4：HUD 和输入

将 `UIController` 拆成常驻 HUD、背包、储物、制作、建造、事件/报告和暂停等子控制器。先继续动态创建控件，不同时引入大规模 `.tscn` 改动。子控制器接收快照并发出意图；旧 UI 方法继续转发。然后把 `main.gd` 的按键处理抽为输入路由，但 `main.gd` 仍是组合根。

### 阶段 5：存档、集成和清理

保持 `SaveSystem` 的文件读写职责，新增协调器按模块收集/恢复片段。完成双向存档契约测试后再替换入口。所有兼容入口先标记 deprecated，至少经过一轮完整回归和运行时验收后再删除。最后统一更新 `Main`、项目设置、runner、README 和架构文档。

## 8. 测试和验收

每个切片按“新模块单元测试 -> 相关旧回归 -> 编辑器解析”的顺序验证。新增测试按 `tests/inventory/`、`tests/survival/`、`tests/world/`、`tests/presentation/`、`tests/persistence/` 等功能目录放置，不争抢同一个根目录烟测文件。

增加静态架构检查，至少验证：领域代码不引用 UI/世界节点、不调用 `get_parent()` 或 `/root/Main`；新模块不直接修改其他模块的内部字典；兼容门面仍存在；地图和存档版本常量没有被迁移改动。

完成前必须通过：

- Godot 编辑器 headless 解析检查；
- README 当前记录的完整回归集和独立音频回归集；
- 资源、温度、日循环、交互、建造、室内、存档、HUD 和音频相关测试；
- 960×540 原生视口与 1920×1080 整数缩放下的正常探索、暂停、背包、储物、制作、建造、事件、报告和结束状态检查；
- 一个模拟跨目录功能切片的合并演练：新增功能模块和测试只改最小适配入口，不改另一功能的内部实现。

完成判定还包括结构性条件：`GameManager` 不绘制或创建 HUD/世界节点；`ExplorationWorld` 不构建 UI；`UIController` 不直接修改资源/阶段内部状态；领域代码不依赖场景树；存档、交互 ID、奖励、碰撞、输入和 HUD 视觉结果与重构前一致。

## 9. 回滚和风险

- 每阶段使用单一职责提交；回退某个切片不会要求回退已合并的契约或其他领域。
- 通过兼容门面保证中间状态可运行；不要在同一提交删除旧入口和迁移所有调用。
- 保存版本和顶层字段不变；任何序列化变化先用旧数据、新数据、往返读写和缺省字段测试锁定。
- GDScript 类型加载问题通过显式 `preload()`、稳定文件边界和每次切片的编辑器解析来控制。
- 节点生命周期问题通过保留当前 `Main` 运行时组装方式来控制，场景资源化不属于第一阶段。
- 如果拆分只增加文件数量却没有独立状态、独立测试或 worktree 价值，则不抽出；避免形式上的过度模块化。

## 10. 不在本阶段

- 改变玩法数值、资源规则、地图布局、HUD 设计或输入绑定；
- 全面事件总线、ECS 或新的场景框架；
- 重新设计音频系统或引入新的第三方素材；
- 提高存档版本或删除历史兼容字段；
- 为了追求目录整齐而把一个垂直功能强行拆到多个独立 worktree；
- 在没有行为测试和运行时证据的情况下删除兼容门面。
